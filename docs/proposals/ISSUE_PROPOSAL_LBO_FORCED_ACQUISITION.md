## 💡 機能提案の背景

「モノポリー」や「いただきストリート」における強制買収は、買収側の手持ち現金で支払える範囲に限られます。現実の M&A では、買収対象の資産や将来収益を担保にした借入（買収ローン）で、手元資金を超える買収を行う LBO（レバレッジド・バイアウト）が広く使われています。本書は、既存の強制買収を LBO へ拡張し、レバレッジの利点と負債リスクを体験できるようにする提案です。

> 📎 **関連提案との整合性:** 本書の当初案に含まれていた次の要素は、既存の提案・実装と重複するため本書の対象から除外しました。実装時に参照する正規仕様は各参照先とします。
>
> - **空売り・追証・踏み上げ:** `ISSUE_PROPOSAL_ADVANCED_STOCK_SYSTEM.md`（リポジトリ直下）に、初期証拠金率40%・維持証拠金率25%・強制決済・残債処理まで定義済みです。
> - **マクロ経済サイクル（景気）と政策金利:** 景気は `src/game/systems/macroEconomy.ts` の `EconomyStatus`・`ECONOMY_FACTORS`・`ECONOMY_TRANSITION_MATRIX` として実装済みです。景気連動の借入金利は `src/game/systems/loan.ts` の `LOAN_INTEREST_RATES` として実装済みです。本書は別系統の「景気指数」を導入しません。中央銀行による量的緩和・引き締めは `ISSUE_PROPOSAL_INNOVATIVE_REALITY_MONEY_GAME.md` で提案済みです。
> - **オプション取引:** `docs/proposals/ISSUE_PROPOSAL_COMPREHENSIVE_ECONOMIC_SIMULATION.md` の「金融派生商品（デリバティブ）とヘッジ」にコール/プットとプレミアムの仕様が定義済みです。
>
> 既存提案に該当がなかった LBO のみを本書の新規性とします。

### 🎯 提案する機能の概要

既存の強制買収（`src/game/economy.ts` の `calculateForceBuyMultiplier`）を拡張し、買収代金のうち手持ち現金で足りない分を、**買収対象エリアを担保とした借入（買収ローン）** で調達できるようにします。買収後は、プレイヤーの手持ち現金から買収ローンを返済していく必要があります。エリアの収益（通行料）が伸びれば返済に回せる現金が増えるため、収益力の高いエリアほど返済しやすくなります。返済が滞るとデフォルトとなり、担保エリアを失います。

### ⚙️ ゲーム内での具体的なメカニクス

1. **買収ローンの組成**
   - 強制買収の支払い時に現金が不足する場合に限り、不足額を買収ローンとして借りられます。
   - 「買収価格」は、既存の `FORCE_BUY` の `cost`（`space.price` × `calculateForceBuyMultiplier` の乗数。ポイズンピルの加算後）を指します。`space.price` ではありません。
   - 担保は買収対象エリア自身です。他プレイヤーからの借入は担保になりません。
   - 借入可能額の上限は買収価格の 70% とし、残り 30% 以上は自己資金で支払います（全額借入による買収は認めません）。したがって、手持ち現金が買収価格の 30% 以上あれば強制買収を提示します。
   - 買収ローンは変動型（`loanType: 'variable'`）とし、`src/game/systems/loan.ts` の `getLoanInterestRate` に従って景気と連動させます。`macroEconomy` が無効、または `economyStatus` がない場合は、既定変動金利 `DEFAULT_LOAN_INTEREST_RATE`（10%）を基準にします。LBO 専用の金利は新設しません。
   - 買収ローンは既存ローンの `Player.loanBalance` とは別のフィールドで管理し、返済 UI・利息計算を既存ローンと分離します。1 人が複数のエリアを強制買収した場合に備え、買収ローンは**担保エリアごとの別契約**とし、`{ collateralSpaceId, principal, balance, overdueInterest, overduePrincipal, remainingLaps, consecutiveOverdue }` の配列で持ちます。返済期間（組成から 4 周）、連続延滞の判定、担保の売却・抵当・交換の禁止、担保処分後の残債は、いずれも契約単位で扱います。担保処分後や担保エリアの強制買収後に残る「担保のない買収ローン」（デフォルト手順 5、下記 4）も同じ配列に `collateralSpaceId: null` の契約として持ちます。この契約は、`principal` を残債、`balance` を残債、`remainingLaps` を 4、`consecutiveOverdue` と延滞額を 0 として新しい契約として作り直し、複数契約の引き落とし順ではこの契約を作成した時点を組成日とみなします。以降の「買収ローン」は、特に断りがない限りこの 1 契約を指します。「総債務」（既存ローン＋買収ローン）の上限を設ける場合は両者を合算して判定します。既存ローンの借入上限（総資産の 50%、`MAX_LOAN_TO_ASSET_RATIO`）とは別枠とし、買収ローン側の上限は買収価格の 70% です。
2. **買収後の返済（周回ごとの分割返済）**
   - 返済期間は組成から 4 周（GO マス通過 4 回）とします。「元本」は組成時の借入額（買収ローンの初期残高）を指します。
   - GO マス通過時に、次の請求額を手持ち現金から自動で引き落とします。判定は GO ボーナス加算後の現金で行います。支払い順は、税 → 既存ローン利息 → 買収ローンとします。税と既存ローン利息は、`src/game/reducer.ts` の GO 処理の現行仕様どおり部分払いをせず全額を引き落とし、本提案では変更しません（現金が負になる場合の扱いも既存仕様に従います）。買収ローンには、その後に残った現金だけを充てます。買収ローンの契約が複数ある場合は、組成が古い契約から順に、それぞれの請求額を残った現金から引き落とします。各契約は、その時点の残り現金を上限に部分払いを受け（実支払額の式は下記の部分払いの項）、請求額に満たない分だけが当該契約の延滞額になります。残り現金が尽きた後の契約は、残り現金が 0 円以下なので実支払額が 0 となり、請求額の全額が延滞になります。延滞は契約ごとに判定するため、同じ GO 通過でも、先に払えた契約は延滞にならず、後続の契約だけが延滞になることがあります。
     - 当該周の利息 = 残債 × 金利（既存ローンと同じく現金から支払い、残債には加算しません）
     - 元本返済額（当周分）= min(元本残高 − 延滞元本, ceil(元本 ÷ 4))。ゲーム内金額は整数のため切り上げとし、最終周に端数を残しません。元本残高は元本のうち未返済の額で、未払いの延滞元本もここに含まれます。延滞元本は次項の請求額で別に請求するため、当周分の元本返済額から引いて二重請求を避けます。繰上返済後も同じ式で請求額を求め、残債（延滞元本を除く）が `ceil(元本 ÷ 4)` を下回る周は残債で頭打ちにします。返済期間（4 周）は変更せず、残債が 0 になった時点で以降の請求はなくなります。
     - 最低返済額 = 元本返済額 + 当該周の利息
     - 請求額 = 最低返済額 + 前周までの延滞額（延滞利息 + 延滞元本）。延滞額は「延滞利息」と「延滞元本」を別々に持ちます（デフォルト時の充当順「延滞利息 → 延滞元本 → 残りの元本」と同じ粒度）。
   - 担保エリアの通行料は通常どおり所有者の現金として受け取るだけで、返済への自動充当は行いません。通行料が発生しない周でも、請求額は期間と残債で決まります。
   - 手持ち現金が請求額に満たない場合は、部分払いを認めます。実支払額 = min(max(0, 手持ち現金), 請求額)（税・既存ローン利息の引き落とし後の現金で判定し、現金が負でも実支払額は負にしません）、延滞額 = 請求額 − 実支払額とし、延滞額は次の GO 通過時の請求額に繰り越します。実支払額は、延滞分（延滞利息 → 延滞元本）を先に、当周分（利息 → 元本）を後に充当します。残債は元本（延滞元本を含む）に充当した分だけ減ります。延滞判定の対象は請求額の全額で、充当後に未払いが残った周を延滞の周とし、残った未払い額が次の周の延滞利息・延滞元本になります。手持ち現金が 0 円以下の周は全額が延滞になります。
   - 増資（設備投資）でエリアの収益を伸ばす、不要な資産を売却（リストラ）して返済に充てる、任意で繰上返済する、といった選択ができます。
3. **デフォルト**
   - デフォルトは契約単位で判定し、デフォルトした契約の担保エリアだけを処分します。他の契約と担保エリアには影響しません。
   - 延滞が 2 周連続した場合（2 回連続の GO 通過で請求額を全額払えなかった場合）、または返済期間（4 周）の終了時に残債もしくは延滞額がある場合はデフォルトとなります。
   - デフォルト時、担保エリアは家を 0 に戻して未所有の状態に戻し、通常の購入対象になります（強制買収時に `houses: 0` へ戻す既存の `FORCE_BUY` と揃えます）。既存の `propertyStates` には銀行という所有者がないため、貸し手（銀行）名義の状態は新設しません。
   - 担保処分後の残債は、LBO 専用の次の手順で確定します。信用取引の残債定義（評価損 − 証拠金残高）には依存しません。
     1. 担保評価額 = `space.price` + `floor(houseCost / 2)` × 家の数（デフォルト確定時点、家を 0 に戻す前の家数で計算）。既存の `SELL_PROPERTY`（オークション）には固定の売却価格がないため、既存の定数（`space.price`、家の売却額 `floor(houseCost / 2)`）から本書で定義します。
     2. 担保評価額を、未払いの延滞利息、延滞元本、残りの元本の順に充当します。
     3. 充当後に残債が残る場合のみ、その額を「担保のない買収ローン」として残します。担保評価額が債務を上回る場合は、超過分をデフォルトしたプレイヤーの現金として返還します。
     4. 買収ローンには `ISSUE_PROPOSAL_ADVANCED_STOCK_SYSTEM.md` の自己破産の閾値（3,000）判定を適用しません。1 契約の借入上限は買収価格の最大 2,400（`space.price` の最大 400 × 乗数 5、ポイズンピル加算で 6）の 70% である 1,680 で、担保処分では債務が増えないため、担保処分後の残債は閾値に届きません。閾値超過時の免除・リスタート（残債の 50% 免除と 300 でのリスタート）も買収ローンには適用しません。
     5. 充当後に残った残債（担保のない買収ローン）は、次の規則で返済を続けます。既存ローン（`Player.loanBalance`）や信用取引の残債とは統合しません。
        - 金利: 継続して発生し、残債 × 金利（組成時と同じ変動金利）を GO 通過時に現金から支払います。
        - 元本返済: 残債 ÷ 4（切り上げ）を新たに 4 周で返済します。組成時からの周回数は引き継ぎません。
        - 再延滞・満期: 延滞が再び 2 周連続した場合、または新たな 4 周の終了時に残債もしくは延滞額がある場合は、処分できる担保がないため、いずれも既存の `DECLARE_BANKRUPTCY` 相当の破産処理へ進みます。担保のない買収ローンには再度の担保処分も期間の延長もありません。

4. **担保エリアの所有権が移動する場合**
   - 担保エリアは、買収ローンを完済するまでは、買収者自身による売却・抵当設定（`propertyStates[].isMortgaged`）・交換の対象外とします。
   - 他プレイヤーによる強制買収（`FORCE_BUY`）の対象にはなります。この場合、買収者（担保エリアの所有者）が受け取る額（`toOwner` と家の取り壊しの返金額 `houseSellBack` の合計）から、延滞利息、延滞元本、残りの元本の順に残債を優先返済します。受取額が残債を上回る分は買収者の現金になります。
   - 受取額で残債を返済しきれない場合、残った額は担保のない買収ローンとして、デフォルト手順 5 と同じ規則（金利継続・残債 ÷ 4 を新たに 4 周・再延滞 2 周連続で破産処理）で請求します。担保を失っても負債は消えないため、強制買収させて負債を踏み倒すことはできません。
   - 買収者が破産宣告をした場合は、デフォルトと同じ手順（上記「デフォルト」の担保処分）で担保を処分します。
   - 上記以外の経路で担保エリアの所有権が動く場合（`ISSUE_PROPOSAL_ADVANCED_STOCK_SYSTEM.md` の独占禁止法による強制売却など）も、売却代金は同じ充当順（延滞利息 → 延滞元本 → 残りの元本）に従います。
   - 担保エリアは二重担保にできません。`ISSUE_PROPOSAL_EVOLUTIONARY_ASSET_MANAGEMENT.md` のシャドーバンキングなど、他の契約の担保に入れることはできません。

> **影響を受ける既存箇所:** 「現金が不足する場合に限り借入」を実現するため、`src/game/reducer.ts` の強制買収の提示判定（`playerAfterRent.money >= forceBuyCost`）と、`FORCE_BUY` の資金チェック（`if (player.money < cost) return state;`）を、手持ち現金が買収価格の 30% 以上あれば通る条件へ変更する必要があります。担保エリアの売却・抵当設定・交換の各アクションにも、完済までの禁止判定が必要です。`DECLARE_BANKRUPTCY` は現状、物件を債権者へそのまま移すため、担保エリアだけ上記「デフォルト」の担保処分を通す分岐が必要です。
>
> 返済期間（4 周）・連続延滞の許容回数（2 周）は初期案の数値です。実装時に既存ローン（`src/game/systems/loan.ts` の GO マス通過時の利息処理）との整合とゲームバランスを検証して調整します。

### 🎓 教材としての教育的効果

- **レバレッジの光と影**: 少ない自己資金で大きな買収ができる一方、収益が伸びず返済に回せる現金が足りなければ、負債に押しつぶされることを体験できます。
- **担保と負債の関係**: 借入の担保になるのは、借りる側が保有する（または買収する）資産であることを理解できます。
- **金利の影響**: 景気連動の金利によって、同じ買収でも返済負担が変わることを学べます。

### ⚖️ ゲームバランスへの影響と懸念点

- **ルールの複雑化**: 初心者には買収ローンの概念が重いため、エキスパートモード限定の機能とするか、段階的にアンロックする形が必要です。
- **買収の連鎖と過度な有利さ**: 資金力のあるプレイヤーが借入を重ねて買収を連鎖させると、ゲームの勝敗が早期に決まる恐れがあります。借入可能額の上限（買収価格の 70%）と、総債務の上限による制限を実装時に検討します。
- **担保評価額と借入比率**: 強制買収の買収価格は `space.price` の 3〜5 倍で、借入は最大でその 70% です。担保評価額は `space.price` 前後のため、返済ゼロでデフォルトすると担保処分後にも残債が残りやすくなります。割高な買収をレバレッジで行うリスクを体験させる意図ですが、借入比率（70%）が LBO の借入規模に対して妥当かは、実装時にゲームバランスを検証して調整します。自己破産の閾値（3,000）は 1 契約の借入上限（1,680）に届かないため、買収ローンでは使いません（デフォルト手順 4）。
- **理不尽な破産**: デフォルトの連鎖が起きやすくなるため、`ISSUE_PROPOSAL_ADVANCED_STOCK_SYSTEM.md` の破産救済の仕組みと整合させる必要があります。
